# fanotify against inotify, measured

**Date:** 2026-09-04 **Host:** reference laptop, kernel 6.17.0-41-generic, x86-64, uid 1000, no
capabilities (`CapEff: 0000000000000000`). **Root filesystem:** ext4 on `/dev/nvme0n1p3`; `$HOME`
is on it. **No Btrfs anywhere on this host.** **Harness:**
`cargo run --release -p templar-fanotify --example fanotify-lab`.

## The question

Recursive inotify cannot cover this machine. `$HOME` holds 189,089 directories after the index's
skip policy, `fs.inotify.max_user_watches` is 250,074, and `WatchBudget::from_limits` deliberately
takes half — 125,037. fanotify's headline answer is `FAN_MARK_FILESYSTEM`: one mark per filesystem
instead of one per directory, which would make the watch-count problem disappear. This is the
measurement of whether that answer is available, and of what the unprivileged variant costs if it
is not.

## Recommendation

**No. Do not replace inotify with fanotify.** Keep `InotifySource` as the default and keep
`FanotifySource` selectable and unadopted. Three findings, in descending order of how much they
settle:

1. **`FAN_MARK_FILESYSTEM` cannot mark a Btrfs subvolume.** It returns `EXDEV` by design, and
   TemplarOS's declared layout is nothing but subvolumes. Variant B is dead for TemplarOS specifically.
2. **Worse: a fanotify group cannot hold marks on two Btrfs subvolumes at once either** — the same
   kernel guard, one branch further down. One `EventSource` is one group, so a single fanotify
   source could not watch `@home` and `@` together. This is a *capability regression* against
   inotify, not a cost difference, and it is not confined to the privileged variant.
3. **Unprivileged fanotify is not cheaper than inotify on the thing that matters.** It is one mark
   per directory, exactly as expected; it buys 6.4% more headroom against the kernel's ceiling
   (266,105 marks vs 250,074 watches) where a home root needs 51% more; it arms 2.5x slower; and it
   costs 2.1x more total memory per directory once the userspace handle map it forces is counted.

A backend that cannot watch the project drive at all, cannot span two subvolumes of the target
layout, and costs more per directory is not an improvement. The watch-count problem is not solved
by changing backend; it is solved by watching fewer directories (Lane B's coverage tiers) and by
treating a dormant, unwatched root as an honest state (Lane C's lifecycle).

## 1. What this process is allowed to do

`fanotify-lab probe`, unprivileged:

| | result |
|---|---|
| `FAN_CLASS_NOTIF` + `FAN_REPORT_DFID_NAME` + `FAN_REPORT_FID` | ok |
| ... + `FAN_REPORT_TARGET_FID` | ok |
| `FAN_CLASS_NOTIF` with **no** fid flags (the classic fd-per-event API) | **EPERM** |
| `FAN_UNLIMITED_QUEUE` / `FAN_UNLIMITED_MARKS` | **EPERM** |
| `FAN_MARK_INODE` on `/`, `$HOME`, `/tmp` | ok |
| `FAN_MARK_MOUNT` on any path | **EPERM** |
| `FAN_MARK_FILESYSTEM` on any path | **EPERM** |
| `open_by_handle_at(2)` on a handle we just obtained | **EPERM** |

So the only fanotify an unprivileged `templar-filed` can have is fid-reporting inode marks — which is
what FSearch 0.3 uses, and which is one mark per directory.

The `open_by_handle_at` result is not incidental. Every fanotify event in fid mode names its
directory by **opaque file handle**, never by path. Turning a handle back into a path needs
`CAP_DAC_READ_SEARCH`. `name_to_handle_at(2)` — path to handle — needs nothing, so an indexer that
already enumerates every directory can build the map itself, which is what `FanotifySource` does.
But that map is one userspace entry per directory, and it is why the memory result below goes the
way it does.

## 2. Arming a tree

100,000 directories under `$TMPDIR`, created and walked before the baseline is taken so the
dentry cache is warm and the slab delta is the marks rather than the walk. Three runs each; the
spread is under 3% on every figure.

| | inotify | fanotify (inode marks) |
|---|---|---|
| watches/marks armed | 100,000 | 100,000 |
| refused | 0 | 0 |
| arm wall time | 0.084 – 0.089 s | 0.215 – 0.220 s |
| per directory | 0.8 – 0.9 us | **2.1 – 2.2 us** |
| kernel `SUnreclaim` delta | 10,192 – 10,392 kB | 7,644 – 7,864 kB |
| per directory | 104 – 106 B | **78 – 81 B** |
| process `VmRSS` delta | 6,640 kB | 28,048 – 28,052 kB |
| per directory | 68 B | **287 B** |
| **total per directory** | **~172 B** | **~366 B** |

fanotify uses about a quarter less *kernel* memory per directory and about four times as much
*process* memory, because arming a directory costs it two extra syscalls (`name_to_handle_at`,
`statfs`) and a hash-map entry keyed by `(fsid, handle_type, handle)`. That map is what makes the
arm 2.5x slower as well. Net: fanotify costs roughly twice as much memory per directory, all in.

Extrapolated to the 189,089-directory home root: inotify ~32 MB, fanotify ~69 MB.

### Against the ceiling

| | ceiling | 189,089 directories |
|---|---|---|
| `fs.inotify.max_user_watches` | 250,074 | 75.6% |
| `fs.fanotify.max_user_marks` | 266,105 | 71.1% |

fanotify buys 6.4% more headroom. The home root already needs 151% of the index's `WatchBudget`
and the project drive adds 172,681 directories more. 6.4% does not change any decision.

## 3. Event throughput and fidelity

200 directories, 20,000 files. Both backends drained by their own reader thread, as
`InotifySource` is built and as `FanotifySource` copies.

**Create + write (`events --files 20000`):**

| | inotify | fanotify |
|---|---|---|
| filesystem operations | 40,000 | 40,000 |
| raw events delivered | 40,000 | 40,000 |
| events per operation | 1.000 | 1.000 |
| delivery rate | 99,205 /s | 98,468 /s |
| queue overflows | 0 | 0 |
| by kind | 20,000 created, 20,000 written | 20,000 created, 20,000 written |

**Create + write + rename + delete, the `cargo build` shape (`burst --files 20000`):**

| | inotify | fanotify |
|---|---|---|
| filesystem operations | 80,000 | 80,000 |
| raw events delivered | 100,000 | 100,000 |
| delivery rate | 244,960 /s | 240,475 /s |
| queue overflows | 0 | 0 |
| by kind | 20,000 each of created / written / moved_from / moved_to / deleted | identical |

**Identical event streams, within 2% on rate.** After normalisation the two backends are
indistinguishable on this workload — including the rename halves, which is the result the next
section is about.

## 4. Renames: fanotify has no cookie, and that is the whole design

inotify pairs a rename with a cookie shared by `IN_MOVED_FROM` and `IN_MOVED_TO`, and
`WatchOwner::pending_moves` (`watch.rs`, `move_pairing_ms = 250`) is built on exactly that.
fanotify's `FAN_MOVED_FROM` and `FAN_MOVED_TO` carry **nothing linking them**. A naive fanotify
backend therefore cannot reconstruct a rename at all: every rename degrades into a delete plus a
create of a file with no history, which in this index means a lost `Mutation::Move` and a
needlessly re-indexed subtree.

`FAN_RENAME` (Linux 5.17) is the answer, and this host accepts it on an inode mark. It delivers
**one** event carrying `FAN_EVENT_INFO_TYPE_OLD_DFID_NAME` and `..._NEW_DFID_NAME` — both
directories and both names, already paired by the kernel. `FanotifySource` splits that back into a
`MovedFrom`/`MovedTo` pair under a synthetic cookie of its own, so `pending_moves` sees exactly the
shape it expects and the pairing is *exact* rather than time-windowed. Observed, verbatim, from a
rename between two marked directories:

```
RENAME
  OLD_DFID_NAME  fsid=(-258360374,-517081569) handle=79290b0c1b060300 name=b"a.txt"
  NEW_DFID_NAME  fsid=(-258360374,-517081569) handle=f09b101c1c060300 name=b"b.txt"
```

A rename out of the watched world arrives with only the `OLD_DFID_NAME` record, so one half is
emitted and `expire_pending_moves` resolves it after the pairing window — the same path inotify
takes. This is a genuine point in fanotify's favour: the kernel does the pairing, so a rename can
never be mis-paired by a timing accident.

## 5. Merging: fanotify loses information inotify does not

fanotify coalesces queued events with the same fid and name into one event with the masks ORed.
inotify never merges. Observed on this host without trying to provoke it — an `mkdir` and the
`rmdir` that followed arrived as a single event:

```
CREATE|DELETE|ONDIR
  DFID_NAME  handle=79290b0c1b060300 name=b"newdir"
```

A merged mask carries no order and no repetition count. Reducing it by priority — the way
`watch.rs` reduces inotify's mask bits — is therefore wrong: the sequence "exists, deleted,
recreated, deleted" merges to `CREATE|DELETE` with the entry **gone**, and picking `Created` leaves
the index holding a file that is not there. `FanotifySource` resolves a mask carrying both an
appearance and a disappearance by asking the filesystem what is there now, and the unit test
`a_create_and_delete_folded_into_one_event_is_resolved_by_looking` pins both directions.

The cost of that correctness is one `lstat` per merged event. In practice merging is rare when the
fd is drained by a dedicated reader thread — which is why the throughput table above shows no
merging at all, and why the merge hazard only appears under a starved reader.

## 6. Queue overflow: identical

`stall --files 40000`: 160,000 filesystem operations generated with nothing reading the fd, then
one drain.

| | inotify | fanotify |
|---|---|---|
| `max_queued_events` | 16,384 | 16,384 |
| events the kernel kept | 16,385 | 16,385 |
| overflow markers | 1 | 1 |

The 16,385th event is the overflow marker itself. Merging bought fanotify no headroom, because
events on distinct names do not merge. **No difference.**

Worth stating for the watcher lane: neither backend overflows in normal operation, because both
drain the kernel fd from a dedicated reader thread and the backlog becomes an in-process channel
instead. An overflow means the reader thread was starved, not that the kernel queue is small.

## 7. The decisive question: `FAN_MARK_FILESYSTEM` on a Btrfs subvolume

**Answer: no. It returns `EXDEV`, by design, and there is no way around it.**

This host is ext4 end-to-end, and `FAN_MARK_FILESYSTEM` needs `CAP_SYS_ADMIN`, which agents do not
have. Two independent lines of evidence, one measured here and one read from the kernel.

### 7.1 The kernel source, v6.17 (`fs/notify/fanotify/fanotify_user.c`)

```c
static int fanotify_test_fsid(struct dentry *dentry, unsigned int flags,
			      struct fan_fsid *fsid)
{
	unsigned int mark_type = flags & FANOTIFY_MARK_TYPE_BITS;
	...
	/*
	 * Make sure dentry is not of a filesystem with zero fsid (e.g. fuse).
	 */
	if (!fsid->id.val[0] && !fsid->id.val[1]) {
		err = -ENODEV;
		goto weak;
	}

	/*
	 * Make sure dentry is not of a filesystem subvolume (e.g. btrfs)
	 * which uses a different fsid than sb root.
	 */
	err = vfs_get_fsid(dentry->d_sb->s_root, &root_fsid);
	if (err)
		return err;

	if (!fanotify_fsid_equal(&root_fsid, &fsid->id)) {
		err = -EXDEV;
		goto weak;
	}
	...
weak:
	/* Allow weak fsid when marking inodes */
	fsid->weak = true;
	return (mark_type == FAN_MARK_INODE) ? 0 : err;
}
```

The comment names Btrfs explicitly. A subvolume's `statfs` fsid differs from the superblock root's,
so `fanotify_test_fsid` reaches `weak:` — and the `weak` fallback is granted **only to
`FAN_MARK_INODE`**. `FAN_MARK_MOUNT` and `FAN_MARK_FILESYSTEM` get the `EXDEV`.

`distro/deploy/layout.toml:44` declares `@`, `@home`, `@var`, `@snapshots`, `@deployments`. Every
one is a subvolume. **`FAN_MARK_FILESYSTEM` cannot mark `@home` on a TemplarOS install.** Variant B is
not a matter of engineering effort; the kernel refuses it.

### 7.2 The second guard, which also kills the unprivileged variant on Btrfs

The same file, `fanotify_set_mark_fsid`, run on **every** mark added to a group:

```c
	/* Do not allow mixing of marks with weak and strong fsid */
	if ((mark->flags ^ old->flags) & FSNOTIFY_MARK_FLAG_WEAK_FSID)
		return -EXDEV;

	/* Allow mixing of marks with strong fsid from different fs */
	if (!fsid->weak)
		return 0;

	/* Do not allow mixing marks with weak fsid from different fs */
	if (old_sb != fsid->sb)
		return -EXDEV;

	/* Do not allow mixing marks from different btrfs sub-volumes */
	if (!fanotify_fsid_equal(&FANOTIFY_MARK(old)->fsid,
				 &FANOTIFY_MARK(mark)->fsid))
		return -EXDEV;
```

Marks on a Btrfs subvolume are *weak*-fsid marks, and the last branch forbids a group from holding
weak-fsid marks from two different subvolumes. One `EventSource` is one group. So on TemplarOS's own
layout, **a single unprivileged fanotify source could not watch `@home` and `@` at the same time**,
with or without `CAP_SYS_ADMIN`. inotify has no such restriction.

### 7.3 Reproduced on this host, on the same code path

`/mnt/Samsung980_1TB` is fuse (`f_type 0x65735546`) and reports `fsid = [0, 0]` — the *other*
branch that reaches `weak:`. Measured with `fanotify-lab probe`:

| group's marks, in order | result |
|---|---|
| fuse mount alone | ok (weak fsid, inode mark) |
| two directories inside the same fuse mount | ok, ok |
| `/tmp` (tmpfs) then `$HOME` (ext4) — two *strong* fsids | ok, ok |
| `/tmp` then the fuse mount | ok, **EXDEV** |
| `$HOME` then the fuse mount | ok, **EXDEV** |
| the fuse mount then `/tmp` | ok, **EXDEV** |

That is `fanotify_set_mark_fsid`'s weak/strong mixing rule, observed. The Btrfs case is the branch
immediately below it. So the mechanism is not merely read from source: its neighbouring branch is
demonstrated here.

**Corollary, and a finding in its own right:** the user's 172,681-directory project drive is fuse.
inotify watches it. A fanotify group can only watch it if it watches *nothing else*. Any index that
holds a home root and a project-drive root behind one fanotify source is impossible today.

### 7.4 What still needs root

`scripts/fanotify-privileged-probe.sh` collects the privileged half into one reviewable script.
**The user must run it**; it is the only step of this lane that agents could not do. It builds the
harness as the invoking user (never as root), then as root runs the capability matrix and one
`FAN_MARK_FILESYSTEM` workload per path, including every subvolume of Lane E's loopback fixture if
`scripts/btrfs-index-fixture.sh setup` has left one mounted. Expected results, stated in advance so
the run is a test rather than an exploration:

* `/` (ext4, fsid == sb root's): `FAN_MARK_FILESYSTEM` **ok**, one mark, negligible slab.
* `@home` on the Btrfs fixture: `FAN_MARK_FILESYSTEM` **EXDEV**.
* `@` on the Btrfs fixture: `FAN_MARK_FILESYSTEM` **EXDEV** (the top-level subvolume `5` is the sb
  root, so the fixture's mount point itself may succeed while `@` does not — worth checking, and
  the script probes both).

If those come back as predicted, nothing in this report changes. If `@home` unexpectedly succeeds,
only section 7.1 is affected — sections 2, 3 and 7.2 still say no.

## 8. Design note for the fd-passing question the plan raised

The plan asked whether `templar-hostd` could open a `FAN_MARK_FILESYSTEM` fd and pass it to
`templar-filed`, since no `org.templaros.Host.*` interface has a `type="h"` argument today. That surface
was **not built**, because the measurement above makes it pointless on the target layout. Recording
what the design would have had to solve, so the question does not have to be re-derived:

* A passed fd carries the *events*, not the *privilege to interpret them*. Every event names its
  directory by opaque handle, and `templar-filed` — correctly — cannot call `open_by_handle_at`
  (measured: `EPERM`). So the receiving daemon still needs a userspace handle-to-path map with one
  entry per directory. The filesystem mark removes the kernel's per-directory cost and leaves the
  indexer's, which is the larger of the two (287 B vs 80 B per directory, section 2).
* It would also hand `templar-filed` a stream of events about **every** file on the filesystem,
  including other users' and the system's — a much wider view than the per-user daemon has any
  business holding, and one polkit cannot narrow after the fact because the fd is not
  path-scoped. That is an ADR-0003 problem before it is a plumbing problem.

Both points survive the Btrfs answer, so they belong in the record even though the mechanism was
not prototyped.

## 9. What was built, and its status

`crates/templar-fanotify` — bindings plus `FanotifySource`, behind the existing
`templar_file_index::watch::EventSource` trait. **Selectable, not default.** Nothing in `templar-filed`
constructs it and the crate is in no service's dependency graph; it exists so this report can be
re-run and so the conclusion can be revisited if the kernel changes.

It is a separate crate because `templar-file-index` is `#![forbid(unsafe_code)]` and should stay that
way, and because no crate in the registry does the job: `rustix` does not implement fanotify at all
(`not_implemented!(fanotify_init)` in 1.1.4), and `nix`'s binding stops at the fixed-size event
header, which in fid mode carries none of the information — the fid records do. The `unsafe`
exception is scoped to `src/sys.rs`: six foreign calls, each one syscall, each with a SAFETY note.
Everything with real logic — decoding the packed event stream, keying directories by handle,
reconstructing a rename, resolving a merged mask — is safe code over `&[u8]`, unit-tested against
hand-encoded kernel layouts. No new external dependency: `libc` is already a workspace dependency
and carries every `FAN_*` constant and every prototype needed.

## 10. Reproducing this

```sh
cargo run --release -p templar-fanotify --example fanotify-lab -- probe /tmp "$HOME" /mnt/point
cargo run --release -p templar-fanotify --example fanotify-lab -- arm --dirs 100000
cargo run --release -p templar-fanotify --example fanotify-lab -- events --files 20000 --dirs 200
cargo run --release -p templar-fanotify --example fanotify-lab -- burst  --files 20000 --dirs 200
cargo run --release -p templar-fanotify --example fanotify-lab -- stall  --files 40000 --dirs 200
sudo scripts/fanotify-privileged-probe.sh          # the only step that needs root
```

The harness is an example rather than a `benches/` target for the reason `watch.rs` documents: the
index's fixture guard panics on a watch root outside `$TMPDIR` whenever the running executable has
a `deps` path component, which every test and bench binary has. Every workload builds its own
fixture under `$TMPDIR` and removes it. Nothing here touches a real home.
